# 企业知识问答系统(RAG)— 项目结构与演示文档

> 本文档用于**项目演示与讲解**,内容包括:项目定位、技术栈、系统架构、目录结构、核心业务流程、数据设计、API 一览、前端页面,以及一份可直接照着走的**演示脚本**。
>
> 项目代码基于 Vue3 + FastAPI + Milvus + MySQL + 通义千问(qwen-max)构建,实现"上传企业文档 → 自动切分向量化 → 基于知识库检索增强生成问答"的完整闭环。

---

## 1. 项目简介

一套**企业私有知识库问答系统**:

- 用户上传企业文档(PDF / PPT / Markdown / TXT),系统自动解析、切分、向量化并存入 Milvus 向量库;
- 用户提问时,系统从知识库中检索相关内容,由通义千问 **qwen-max** 结合检索结果**流式生成**回答,并**标注引用来源**;
- 支持多知识库、多文档管理;每个知识库独立检索空间;
- 采用**父子分块**策略:小子块负责检索(粒度细、命中准),父块作为上下文(信息完整、连贯),兼顾召回准确率与生成质量;
- 支持**稠密向量检索**与**混合检索(向量 + BM25 关键词 + RRF 融合)**两种模式。

### 核心能力一览

| 能力 | 说明 |
|---|---|
| 多用户认证 | 注册 / 登录 / JWT Token / 图形验证码 |
| **角色权限** | **三级角色 + 部门隔离**(见下方权限矩阵) |
| 知识库管理 | 创建 / 删除 / 编辑,每库独立 collection,可配置检索方式与分块参数 |
| 文档管理 | 上传 / 删除 / 解析进度实时展示 / 文档块浏览 |
| 文档解析 | PDF、PPT/PPTX、Markdown、TXT;图片暂不 OCR |
| 父子分块 | 父块(上下文粒度,默认 2000 字)+ 子块(检索粒度,默认 500 字) |
| 向量化 | 通义 DashScope text-embedding(1024 维) |
| 向量存储 | Milvus(每知识库一个 collection,显式 schema) |
| 混合检索 | 向量召回 + BM25 关键词召回 → RRF 融合 |
| 上下文映射 | 命中子块 → 映射回父块(去重、保序)作为 LLM 上下文 |
| 流式问答 | SSE 逐 token 输出,带历史对话(默认 5 轮) |
| 引用标注 | 回答关键信息标注来源编号 [1]、[2] |

**权限矩阵(三级角色 + 部门):**

| 操作 | super_admin(系统管理员) | dept_admin(部门管理员) | employee(员工) |
|---|---|---|---|
| 查看知识库 | 所有部门 | 本部门 | 本部门 |
| 用知识库问答 | ✅ | ✅ | ✅ |
| 创建/删除/编辑知识库 | 所有部门 | 本部门 | ❌ |
| 上传/删除文档、编辑块 | 所有部门 | 本部门 | ❌ |
| 查看文档与块 | ✅ | ✅ | ✅ |

- 部门:知识库创建时选择所属部门,数据由 `scripts/init_rbac.py` 种子 + SQL 维护;
- 角色:注册用户默认 `employee`;`super_admin` / `dept_admin` 由管理员 SQL 指定;
- 权限在**后端强制校验**(`require_admin` 依赖 + 部门可见性),前端按钮只是体验层。

## 5. 核心业务流程

### 5.1 文档上传与向量化(写入链路)

```
上传文件(POST /api/knowledge-bases/{kb}/documents)
  │ ① 大小校验(≤10MB,超限返回 413 明确提示)
  │ ② 保存原始文件到 data/uploads/{kb_id}/
  │ ③ MySQL 落库 Document 记录(status=pending),kb.doc_count + 1
  ▼
后台异步解析(threading,接口立即返回,前端轮询 /progress 展示真实进度)
  │ ④ parse_file:按类型解析出纯文本(PDF 逐页 / PPT 逐页 / MD/TXT 直接读)
  │ ⑤ 父子分块:
  │     父块切分(chunk_size=parent_chunk_size 默认 2000,重叠 50)
  │     → 每个父块内再切子块(chunk_size=500)
  │ ⑥ 父块写入 MySQL(不向量化,parent_id=NULL,作为"上下文单元")
  │ ⑦ 子块写入 Milvus(metadata 带 kb_id / document_id / parent_id / chunk_index)
  │ ⑧ 子块落 MySQL(指向父块 id,记录 milvus_id)
  ▼
Document.status = completed,chunk_count = 子块数
```

**Milvus collection 设计(每知识库一个,显式 schema):**

| 字段 | 类型 | 说明 |
|---|---|---|
| text | VARCHAR | 子块文本(检索单元) |
| pk | INT64(主键,自动) | 向量主键 |
| vector | FLOAT_VECTOR(1024) | 通义 embedding 向量 |
| kb_id | INT64 | 知识库 id |
| document_id | INT64 | 文档 id |
| parent_id | INT64 | 所属父块 id(父子分块关键) |
| chunk_index | INT64 | 块序号 |

> 显式声明 schema(而非靠首次插入推断),保证新旧版本行为一致、字段完整。

### 5.2 问答流程(读取链路)

```
用户提问(POST /api/chat/stream,SSE)
  │ ① 会话管理(自动建会话 / 取历史,默认 5 轮)
  │ ② 多知识库检索:
  │     向量召回:问题 → embedding → Milvus similarity_search(top 20)
  │     关键词召回(hybrid 模式):BM25 在子块语料上检索(top 20)
  │     → RRF 融合,取 top 10
  │ ③ 父子分块映射:命中子块 → 查 MySQL 取对应父块(去重、保持相关度顺序)
  │ ④ 构建上下文(取前 final_top_k=5 个父块,标注来源文档 id)
  │ ⑤ 组装提示词(系统约束 + 历史 + 参考资料 + 问题)
  │ ⑥ qwen-max 流式生成 → SSE 逐 token 返回前端
  │ ⑦ 结束后保存助手消息
  ▼
前端逐字渲染;回答中 [1][2] 标注引用来源
```

### 5.3 删除链路

- **删文档**:删 Milvus 向量 + 删 MySQL chunk 行 + 删本地文件 + `doc_count -= 1`;
- **删知识库**:先 `drop_collection` 删 Milvus collection,再删 chunk/document/知识库记录,不留脏数据。

### 第一步:环境准备(1 分钟)

### 第二步:创建知识库并上传文档(2 分钟)

2. 进入详情页 → 上传 PDF → 展示**实时解析进度条** → 完成后文档状态变"已完成",显示块数;
3. 再传一个 Markdown,展示多文档共存;
4. 点开文档 → **文档块预览**:说明哪些是父块(完整段落),子块是检索单元(可编辑/删除)。

### 第三步:问答演示(3 分钟)
1. 进入**对话**页,勾选知识库;

### 第四步:系统能力收尾(1 分钟)

## 11. 演示时的讲解要点

- **父子分块为什么好**:子块小 → 检索命中更精准;父块大 → 交给大模型的上下文更完整、不碎片化;
- **混合检索为什么好**:向量召回理解语义(同义改写也能命中),BM25 保证关键词精确匹配兜底,RRF 融合两路结果;
- **流式问答**:SSE 协议,逐 token 渲染,体验接近 ChatGPT;
- **引用标注**:回答附 [1][2] 来源编号,提升可信度,便于溯源;
- **异步解析**:上传立即返回,后台线程解析 + 轮询进度,大文件不阻塞接口;
- **架构分层**:FastAPI 路由/服务/模型分层、前端组件化、Docker Compose 一键编排,体现工程化能力。
