# 技术改进:三级权限体系与部门隔离

> 日期:2026-08-24
> 涉及:用户/知识库模型、权限校验、前端角色控制
> 对应需求:用户权限分级;知识库增删仅管理员;对话人人可用;按部门共享知识库

---

## 1. 变更概述

原系统为**扁平权限模型**:所有登录用户权限相同,知识库按 `user_id` 私有隔离,无角色、无部门概念;
任何人都能创建/删除知识库、上传/删除文档。

本次引入 **三级角色 + 部门隔离 + 公开知识库**:

- `super_admin`(系统管理员):可见/管理所有部门;
- `dept_admin`(部门管理员):管理本部门知识库与内容;
- `employee`(员工,默认):仅可见本部门(及公开库),可查看与问答,不能管理内容;
- 公开知识库(`is_public`):所有登录用户可见可用,仅超级管理员可建可管;
- 权限在**后端强制校验**,前端按钮仅为体验层;前端启动时经 `/auth/me` 从后端同步角色(修复旧登录态导致的管理员被识别为员工问题)。

---

## 2. 新旧功能对比

| 场景 | 旧行为 | 新行为 |
|------|--------|--------|
| 注册用户角色 | 无角色概念 | 默认 `employee`,可指派 `dept_admin` / `super_admin` |
| 知识库可见范围 | 仅创建者本人 | 本部门用户(员工/部门管理员)+ 超管全部;公开库全员可见 |
| 创建/删除/编辑知识库 | 任何登录用户 | **仅管理员**;dept_admin 仅本部门,公开库仅超管 |
| 上传/删除文档、编辑块 | 任何登录用户 | **仅管理员**(dept_admin 限本部门,公开库仅超管) |
| 用知识库问答 | 任何人可用任何库 | 任何人可用**本部门 + 公开**库 |
| 部门归属 | 无 | 用户/知识库均归属部门;创建知识库必须选部门 |
| 公开知识库 | 无 | 超管可建"全公司可见"库,全员可见可用 |
| 前端权限展示 | 所有按钮人人可见 | 按角色隐藏创建/删除/上传/编辑按钮 |
| 旧登录态(改版前登录) | 前端读不到角色,管理员被当员工 | 启动时 `/auth/me` 从后端同步,自动修正 |

## 4. 数据与接口变化

**表结构(新表/新列,`scripts/init_rbac.py` 幂等迁移):**

| 表 | 变化 |
|----|------|
| `departments`(新表) | id / name / created_at |
| `users` | + `role`(默认 employee)、+ `department_id` |
| `knowledge_bases` | + `department_id`(必填)、+ `is_public`(默认 0) |

**API 变化:**

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/login` | 响应增加 `role` / `department_id` / `department_name` |
| GET | `/api/auth/me` | **新增**:当前用户信息(含角色/部门) |
| GET | `/api/departments` | **新增**:部门列表 |
| POST/PUT/DELETE | `/api/knowledge-bases[/{id}]` | 改为**仅管理员**;创建必填 `department_id`,可带 `is_public` |
| POST | `/api/knowledge-bases/{id}/documents`、`PUT/DELETE /api/chunks/{id}` | 改为**仅管理员** |
| GET | `/api/knowledge-bases` | 返回本部门 + 公开库 |

## 5. 影响与注意事项

- **兼容性**:存量用户默认 `employee` 且无部门,未指派部门前仅可见公开库;存量知识库由迁移脚本回填到"默认部门";
- **权限在后端**:前端隐藏按钮只是体验,真正校验在 `require_admin` / 可见性判断,直调接口会被 403;
- **角色即时生效**:`require_admin` 每次从 DB 读取角色,改角色无需等 token 过期;
- **管理员指派**:注册入口保持开放,角色由 SQL 指派(见 `docs/使用说明.md`)。
